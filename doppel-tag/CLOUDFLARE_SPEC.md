# Cloudflare 通信・運用仕様（追補）

現行仕様書 16 節「リアルタイム通信の構成」および 18 節「Cloudflare」に対する追補。
現行実装が身内試遊向け（1 DO に最大 4 部屋・24 接続）である前提で、
**公開前に決めておくべき構成と運用**を記述する。

---

## 1. Durable Object の分割 — 現行構成の最優先の変更点

### 1-1. 現状の問題

現行：**1 つの Durable Object に複数部屋と SQLite（XP・アカウント）が同居している。**

Durable Object は**シングルスレッド**である。これが以下を引き起こす。

| 問題 | 内容 |
|---|---|
| 部屋同士の干渉 | 4 部屋 × 20Hz ＝ 80 tick/秒を 1 スレッドで処理する。1 部屋の AI がスパイクすると**他の部屋も遅延する** |
| 認証が試合を止める | 18 節が自ら挙げている懸念。scrypt(N=32768) は**意図的に重い**。同じ DO 内で実行すれば、その間 tick が止まる |
| 水平に伸びない | 部屋を増やすには DO を強くするしかないが、DO は強くできない |

**scrypt の実行時間が 1 tick（50ms）を超えた瞬間、その DO の全部屋が同時にカクつく。**
これは実回線試遊で「原因不明の同期の乱れ」として現れ、最も再現しづらい種類の不具合になる。

### 1-2. 推奨構成

```text
Worker（ルーティング・静的配信・Turnstile 検証）
 ├─ RoomDO      … 1 部屋 = 1 DO。試合の進行。永続化なし（メモリのみ）
 └─ AccountDO   … 1 ユーザー = 1 DO。SQLite に認証情報・XP・スキル
```

| DO | ID の作り方 | 保存 |
|---|---|---|
| `RoomDO` | 部屋ごとに一意（1-3 参照） | **不要。**試合はメモリのみ。仕様書どおり再起動で復元しない |
| `AccountDO` | `idFromName(userIdの正規化済み小文字)` | SQLite。認証・XP・スキル・セッション |

**得られるもの：**

- 部屋が互いに干渉しない。1 部屋が重くても他部屋に影響しない
- **認証処理がユーザーごとの DO に分散する。**scrypt が試合の tick を止めない
- 部屋数が水平にスケールする
- 試合 DO は永続化を持たないので、SQLite の同期書き込みで tick が止まることもない

XP の加算は `RoomDO → AccountDO` の DO 間呼び出しで行う。
18 節の「未保存 XP をメモリに保持して 1 秒おきに再試行」はそのまま使えるが、
**RoomDO 側のキューはプロセス終了で消える**ので、
試合終了時ではなく**獲得のたびに送る**方が耐久性が高い（1 人あたり 10 秒ごと＋奉納時なので頻度は低い）。

### 1-3. 部屋 ID と地理的配置 — 見落としやすい落とし穴

**Durable Object は「最初に作られた場所」に固定され、後から移動しない。**

`idFromName(部屋コード)` を使うと、ID が決定論的になる代わりに、
**作成場所を指定できない。**日本のプレイヤーの部屋が欧州に作られると、
往復で 200ms 以上の固定遅延が乗る。

**対策：**

```
1. 部屋作成時に newUniqueId({ locationHint: 'apac' }) で RoomDO を作る
2. 部屋コード（英字6文字）→ DO ID の対応を KV に保存（TTL 例：2時間）
3. 参加者は部屋コードから KV を引いて DO ID を得る
```

`locationHint` は `apac` / `wnam` / `enam` / `weur` / `eeur` / `sam` / `afr` / `oc` から選ぶ。
主な想定プレイヤーが日本なら `apac`。

**なお locationHint はヒントであり保証ではない。**
実回線試遊で RTT を実測し、想定と違えば見直すこと。

## 2. 20Hz のゲームループをどう回すか

仕様書に記述がないが、Workers 上では自明でない。

### 2-1. 採用すべき方式

**`setInterval(tick, 50)` を DO 内で回す。** Alarm API は 50ms 間隔には使わない。

```
・最初の参加者が接続したら setInterval を開始
・最後の参加者が切れたら clearInterval し、部屋を破棄
・Alarm は粗い粒度の用途にのみ使う（空室の掃除、切断保持30秒の期限、試合の最大時間）
```

### 2-2. WebSocket Hibernation は試合中に使わない

Hibernation API を使うと DO がメモリから退避され、**進行中の試合状態が失われる。**

| 場面 | Hibernation |
|---|---|
| 試合中（`setInterval` 稼働中） | **使わない** |
| ロビーで待機中 | 使ってよい |
| 観戦のみが残っている状態 | 使わない（試合は継続中） |

**この区別を実装とドキュメントに明記すること。**
「Hibernation で課金を減らす」という一般的な助言を、
リアルタイム部分にそのまま適用すると試合が壊れる。

### 2-3. tick の実測を必ず取る

1 tick の処理時間を計測し、**p99 が 50ms を超えたら警告**を出す。
6 人＋敵最大 5 体＋AI＋当たり判定＋JSON 化を 50ms に収める必要がある。
現状の「部屋ごとに一度 JSON 化」は、3 節の対策を入れるまでは tick の主要なコストになりうる。

## 3. 状態配信 — 帯域と情報露出の両方に効く改修

### 3-1. 現状の試算

16 節：「状態は部屋ごとに一度 JSON 化し参加者へ配信」を 20Hz。

actor（座標・向き・種別・外見・呪い・水分・停止期限・スキル・装備・演出期限）が
最大 11 体前後、item が 20 個前後。JSON だと 1 フレーム **2〜4 KB** 程度になる。

```
3 KB × 20 Hz ＝ 60 KB/s ＝ 約 480 kbps（1 人あたり、下り）
```

**携帯回線・電波の弱い場所では厳しい。**また DO 側は
`JSON.stringify` を毎 tick 実行し、それを人数分送信する。

### 3-2. 3 段階の改修（効果が大きい順）

**(a) 送らないものを決める — 最優先。4 節と同じ対策。**

`kind`、`copyId`、AI の内部状態、未取得アイテムの一部を送らない。
**情報露出（4 節）の対策がそのまま帯域削減になる。**

**(b) 差分配信**

前フレームから変化したフィールドだけ送る。
静止している actor、取得されていない item は送らない。
**5 秒に 1 回はフルスナップショットを送る**（取りこぼしの復旧用）。

**(c) バイナリ化**

| フィールド | 表現 |
|---|---|
| 座標 | 固定小数点 16 bit（94m 四方なら 1.5mm 精度で十分） |
| 角度 | 8 bit（1.4 度刻み。表示は 45 度 8 方向なので過剰なほど） |
| 各種フラグ | ビットフィールド |
| 期限（stunUntil 等） | 試合時刻からの相対値を 16 bit |

(a)+(b)+(c) で **1/5〜1/10** になる。`JSON.stringify` の CPU も同時に減る。

### 3-3. bufferedAmount が取れない問題への代替策

16 節が挙げている、Cloudflare の WebSocket では `bufferedAmount` が取得できず
送信詰まり保護ができない件。

**代替策：**

1. **送信量そのものを減らす**（3-2）。これが最も効く
2. **heartbeat の往復で詰まりを検出する。**現行の約 2 秒間隔の heartbeat に対し、
   pong が一定回数返らない接続を切る（現行の 7 秒判定を流用できる）
3. **アプリ層のシーケンス確認。**クライアントが「最後に処理したスナップショット番号」を
   入力に含め、サーバーは**遅れが一定フレーム以上の接続へ送る頻度を下げる**
   （20Hz → 10Hz に落として救済し、それでも追いつかなければ切断）
4. 1 接続あたりの送信バイト数を自前で積算し、上限超過で切断

## 4. 情報露出 — 一般公開の前提条件

### 4-1. 深刻度の評価

16 節・20.5 節が「改造クライアントは敵種別や座標を調べられる」と記述している。
**これは一般公開においては P0 である。**

理由は、協力ゲームだからこそ悪い。

- 対戦ゲームなら「チートした本人が有利になる」だけだが、
  本作では **1 人が調べれば、その人が『あいつがドッペルだ』と言うだけで部屋全体の緊張が消える**
- 悪意がなくても起きる。開発者ツールを開いて WebSocket フレームを眺めるだけで分かる
- 本作の価値のほぼ全部が「目の前の相手が仲間か分からない」ことに乗っている

### 4-2. 最小限で最大の効果がある対策

**`kind` と `copyId` をクライアントへ送らない。これだけで被害の大半が消える。**

- 見た目は「魚種・名前・ズボン色」の外見フィールドだけで完全に表現できる
- ドッペルと探索者を**同じ形の actor** として配信する
- AI の偽装動作（飲水のふり、拾うふり）も、**本物と同一のイベントとして**配信する
  （14.2 節が既に「専用の見分け表示はない」としているので、通信層でもそれを守る）
- 撃退・消失・出現は、クライアントには「actor が消えた／現れた」としか見えないようにする

### 4-3. 位置露出への対策（段階的に）

| 段階 | 内容 | 副作用 |
|---|---|---|
| 1 | `kind`・`copyId` を送らない | なし。**まずこれだけやる** |
| 2 | 壁で完全に遮蔽され、かつ 20m 以上離れた actor を送らない | 視界に入る瞬間のポップイン。補間バッファに 1 フレーム分の猶予を持たせて緩和 |
| 3 | 視線判定ベースの関連性フィルタ | 角を曲がった瞬間の表示遅れ。実装コストが高い |

**段階 1 は必須。段階 2 は一般公開時。段階 3 は当面不要。**

段階 2 を入れると、足音は「聞こえるが姿は送られていない」状態になる。
**音のために位置が必要な場合は、正体を含まない「音イベント」として配信する**
（発生座標・種類・時刻のみ。誰が鳴らしたかは送らない）。
これは 8.1 節の「匿名の通知」と同じ思想で一貫する。

### 4-4. 脅威モデルの線引き

仕様書が求めている区別を、以下のとおり明文化することを推奨する。

| 対象 | 方針 |
|---|---|
| 身内試遊 | 現行のままでよい。参加者が自分で壊さない前提 |
| 招待制の限定公開 | 段階 1 必須 |
| 一般公開 | 段階 1・2 必須。加えて 8 節の運用監視 |

## 5. 静的配信とキャッシュ

Workers Static Assets で配信する際、**キャッシュ設計を明示的に決めること。**
現行仕様に記述がなく、放置すると初回ロードのたびに音声 8MB を再取得しうる。

| 対象 | ファイル名 | `Cache-Control` |
|---|---|---|
| JS / CSS（Vite がハッシュ付与） | `assets/*.[hash].js` | `public, max-age=31536000, immutable` |
| 音声・作画・画像 | **内容ハッシュを付与する** | `public, max-age=31536000, immutable` |
| `manifest.json` | ハッシュなし | `public, max-age=60` |
| HTML | ハッシュなし | `no-cache` |

**作画素材（72 シート）と音声には現状ハッシュが付いていない可能性が高い。**
ビルド時にハッシュ付きファイル名へ変換し、`manifest.json` で参照する形にすると、
更新時のキャッシュ不整合と、無駄な再取得の両方が解決する。

Brotli / gzip は Cloudflare 側で自動的にかかるが、**WAV には効かない。**
BGM_SPEC.md 6-2 の Opus 化を行えば、この問題は根本から消える。

## 6. デプロイと更新 — 進行中の試合を壊さないために

17 節：「Durable Object の再起動・コード更新をまたぐ試合復元はない。」

**つまり `wrangler deploy` を打つたびに、遊んでいる人の試合が飛ぶ。**
身内試遊なら許容できるが、公開後は運用手順が要る。

### 6-1. ドレイン（新規受付停止）手順

```
1. KV または環境変数のフラグ `acceptNewRooms = false` を設定
2. Worker は新規部屋作成を拒否し、「まもなく更新します」を返す
3. 進行中の試合が終わるのを待つ（最大 12 分 ＋ 切断保持 30 秒）
4. 全 RoomDO が空になったことを確認
5. wrangler deploy
6. acceptNewRooms = true
```

KV フラグ方式なら、**デプロイせずに新規受付だけ止められる**（KV の反映は数十秒）。
環境変数方式だとフラグ変更自体がデプロイになるので、KV を推奨する。

### 6-2. ロールバック

`wrangler rollback` または Cloudflare ダッシュボードのバージョン一覧から戻す。
**デプロイ前に必ず現行バージョン ID を記録すること。**

### 6-3. 段階的公開（Gradual Deployments）

Worker のトラフィックを % 指定で新旧に分けられるが、
**Durable Object が絡む場合は注意が要る。**
新旧のコードが同じ DO クラスを触るため、状態の形が変わる更新では破綻する。

**本作では Gradual Deployments を使わず、6-1 のドレイン方式を採ること。**
試合が最大 12 分で必ず終わる設計なので、ドレインが現実的な時間で完了する。
これは本作の短い試合時間が運用面でも効いている例。

## 7. 秘密情報とリポジトリ

20.4 節に「現ワークスペースはまだ Git リポジトリ未初期化」とある。
**最初のコミットの前に `.gitignore` を用意すること。**認証情報の誤コミットは、
一度履歴に入ると取り消しが面倒になる典型的な事故。

```gitignore
node_modules/
dist/
.wrangler/
.dev.vars
.dev.vars.*
*.local
test-results/
# ローカル検証用のプロフィール・アカウント保存先
data/
*.sqlite
*.sqlite-journal
```

| 秘密情報 | 置き場所 |
|---|---|
| Cloudflare API トークン | `wrangler login` の認証情報。**リポジトリに置かない** |
| セッション Cookie の署名鍵 / ペッパー | `wrangler secret put`。ローカルは `.dev.vars` |
| Turnstile のシークレットキー | `wrangler secret put` |

23 節が「認証トークン、ブラウザ保存 ID、実プレイヤーのプロフィール、
Cloudflare の認証情報を含めない」と正しく書いているので、
**`.gitignore` でそれを機械的に担保する。**

### 8-2. バランス調整用のテレメトリ — 現状の欠落

仕様書には「試遊で調整する」が**14 箇所以上**現れるが、
**調整の根拠となるデータを取る仕組みが記述されていない。**

体感だけで水の再出現間隔や 60 秒クールダウンを調整するのは難しい。
以下を試合終了時に 1 レコード送るだけで、調整の質が大きく変わる。

| 項目 |
|---|
| モード（6 分／12 分）、人数、練習かどうか |
| 勝敗、経過時間、保管札数 |
| 各プレイヤーの：被掴み回数、脱落の有無と原因（掴み／水切れ）、生存時間 |
| 撃退回数（コピー元／それ以外の別） |
| 仲間確認の掴み回数（＝ 60 秒クールダウンの消費理由） |
| 飲水回数、水切れ猶予に入った回数 |
| 札の初回取得までの時間、祠への平均運搬時間 |
| 天井落下の発生回数、手鏡の使用回数と使用時間 |
| 装備の取得・使用回数（種類別） |

**個人を特定しない集計値にとどめること**（ユーザー ID ではなく試合単位の匿名 ID）。
プライバシーポリシー（9 節）との整合も取る。

## 10. 費用の制御

Durable Objects は**アクティブ時間と リクエスト数の従量課金**で、
**課金上限で自動停止する仕組みはない。**

12 分の試合は、その部屋の DO が 720 秒間アクティブであり続けることを意味する。
20Hz で動くため、アイドル状態にならない。

**確実な防御はアプリ側の上限だけである。**

| 対策 | 内容 |
|---|---|
| 同時部屋数の上限 | 現行の「最大 4 部屋」を公開時に引き上げる際は、**慎重に段階的に** |
| 同時接続数の上限 | |
| 空室の即時破棄 | 最後の 1 人が切れたら `clearInterval` して DO を解放（2-1） |
| 放置部屋のタイムアウト | Alarm で検出し破棄 |
| **予算アラート** | Cloudflare ダッシュボードで通知を設定 |
| **アカウント乱造対策** | 登録画面に **Turnstile**（Cloudflare の無料 CAPTCHA 代替）を入れる。18 節が課題として挙げている件への最も簡単な解 |

公開直後は**同時部屋数を意図的に低く設定し、実測してから上げる。**
上限に達したら「満員です」を返す設計が、想定外の請求に対する唯一確実な歯止めになる。

| シナリオ | 期待する結果 |
