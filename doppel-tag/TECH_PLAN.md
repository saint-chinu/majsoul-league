# 技術計画・実装ロードマップ

## 1. 実装可能か — 結論

**可能。** ただし難易度の内訳は直感と違うところにある。

| 要素 | 難易度 | 備考 |
| --- | --- | --- |
| 3D キャラの移動・カメラ | 低 | エンジン標準機能でほぼ済む |
| 背後からの掴み判定 | 低〜中 | 内積と Raycast。設計次第で劇的に楽になる（3-2 節） |
| 顔の醜悪化演出 | 低 | ブレンドシェイプ 3 段階 + マテリアル差し替え |
| 見た目のコピー | 低 | プリセットアバターに限定すれば ID の差し替えだけ |
| ネットワーク同期（6 人） | **中〜高** | ここが本丸。ただし 6 人なら P2P で足りる |
| 正体の秘匿（チート耐性） | **高** | 3-3 節。設計で握り潰す必要がある |
| 近接ボイスチャット | 中 | 既製ミドルウェアで解決 |
| ドッペル AI（探索の素振り） | **最高** | 人間プレイヤーにすれば消える |
| マップ制作 | 中（ただし物量） | 見た目より「見通しの悪さ」の設計が重要 |
| アニメーション | 中 | 掴む／掴まれて振り返る、は自作かモーションキャプチャが要る |

**工数が集中するのはネットワークとマップ制作、そしてアニメーション。**
ゲームロジック自体は驚くほど軽い。

---

## 2. エンジン選定

### 推奨：Unreal Engine 5

理由：

- **キャラクター移動のネットワーク同期（CharacterMovementComponent）が標準で完成している。**
  クライアント予測・サーバ照合・巻き戻しまで込み。これを自作するのは数か月仕事なので、
  ここが無料で手に入る意味は大きい
- Lyra サンプルにマルチプレイの雛形が揃っている
- 暗所・ライティング・ポストプロセスの質が高く、ホラーの絵が作りやすい
- MetaHuman があるが、**このゲームでは使わないこと**（後述 4-1）
- Blueprint でプロトタイプが早い。ネットワーク（Replication / RPC）も Blueprint で書ける

### 対抗：Unity + Fish-Net（または Netcode for GameObjects）

- C# の方が書きやすいならこちら。ただし移動同期は自前で詰める部分が多い
- Fish-Net は無料で機能が厚く、Netcode for GameObjects より実戦的
- Steam 連携は Facepunch.Steamworks / Steamworks.NET

### 非推奨：Godot

4.x のマルチプレイは軽量な用途なら十分だが、キャラクター移動の予測・補正を自分で書くことになる。
このジャンルでそこに時間を溶かす価値は薄い。

**判断基準：**チームに UE か Unity の経験者がいるなら、その方。どちらもゼロなら UE5。

## 3. ネットワーク設計

### 3-1. トポロジ

**リッスンサーバ（ホストがプレイヤーを兼ねる）＋ Steam のリレー（SDR）** を推奨。

- 6 人程度なら帯域・CPU ともに余裕
- 専用サーバ費用がゼロ
- Steam Datagram Relay で NAT 越え問題と IP 露出が解決する
- UE5 なら `OnlineSubsystemSteam`、Unity なら FizzySteamworks / Steamworks トランスポート

将来的に野良マッチを本格運用するなら専用サーバへ移行するが、**MVP では不要**。

### 3-2. 掴み判定 — 設計で実装を楽にする

素直に作ると「背後判定」はネットワークの難所になる。撃つゲームと同じ
**ラグ補正（過去のフレームまで巻き戻して判定する処理）**が必要になり、実装が跳ね上がる。

**回避策：掴みを即時ヒットではなく「予備動作を伴うアクション」にする。**

```
1. 掴みボタンを押す → 0.3〜0.4 秒の手を伸ばすモーション（この間キャンセル不可、移動速度低下）
2. モーション終了時点でサーバが判定
3. 判定条件（すべてサーバ権威）
   - 距離が 1.5m 以内
   - dot(掴む側の前方ベクトル, 相手の前方ベクトル) > 0.3   ← 同じ方向を向いている＝背後にいる
   - dot(掴む側→相手のベクトル, 相手の前方ベクトル) > 0     ← 相手の背中側に立っている
   - 両者の間に遮蔽物がない（Raycast）
4. 成立ならサーバが全員に結果をブロードキャスト
```

予備動作を挟むことで 100〜200ms の遅延が体感に埋もれ、**ラグ補正が丸ごと不要になる。**
そしてゲーム的にも「読まれると避けられる」という駆け引きが生まれるので、
実装都合の妥協ではなく設計の改善になっている。

同様に、**掴まれた側の強制振り向き（0.8〜1.2 秒のカメラ演出）**も、
その間に状態同期を全員に配り切るための緩衝時間として機能する。演出と技術が一致している。

### 3-3. 正体の秘匿 — 見落とされがちな最重要課題

「誰がドッペルか」はクライアントに送ってはいけない情報。だが素朴に実装すると漏れる。

**必須の実装方針：**

- サーバは「真の ID」と「見かけの ID」を分けて持つ
- **各クライアントには見かけの ID しか送らない。**真の ID をクライアントに複製（Replicate）しない
- UE なら Actor の `NetOwner` 単位で可視性を制御する、あるいはドッペル状態を
  本人のクライアントにのみ送る（UE の `COND_OwnerOnly` 相当）
- 位置情報も、視界外のプレイヤーは可能なら送らない（関連性フィルタリング）。
  完全なウォールハック対策は難しいが、送らないものは覗けない

**リッスンサーバの構造的な弱点：ホストがドッペルの場合、ホストは全情報を持つ。**
逆にホストが生存者の場合、ホストのメモリには全員の真の ID がある。
つまり **P2P では原理的にホストのチートを防げない。**

対処：

- MVP・フレンド間プレイでは**割り切る**（このジャンルの多くがそうしている）
- 公開リリース時は、正体判定に関わる部分だけでも専用サーバに寄せる
- 最低限、ホストをランダムなプレイヤーに固定せず、ロビー主に固定しない（効果は限定的）

この論点は「後から直せない」種類なので、**最初にどこまで割り切るかを決めておくこと。**

### 3-4. 権威の分配

| 処理 | 権威 |
| --- | --- |
| 移動 | クライアント予測＋サーバ照合（エンジン標準に任せる） |
| 掴みの成否 | **サーバのみ** |
| 変身 | **サーバのみ**（クールタイム管理も含む） |
| アイテム取得 | **サーバのみ** |
| 時間ゲージ | **サーバのみ** |
| 演出（顔の変形、カメラ、音） | クライアント（サーバの結果通知を受けて再生） |

## 4. アセットと演出

### 4-1. キャラクター

**MetaHuman や高精細な自作キャラは使わないこと。**理由：

- 6 体分の高解像度キャラを暗所で描画するのは無駄が多い
- コピー実装のために全員が同じリグ・同じ体型である必要がある
- 顔を 3 段階に変形させるブレンドシェイプを、リアル頭部で破綻なく作るのは大変

**推奨：スタイライズされたプリセットアバター 6〜8 体。**
全員同一のスケルトンを共有し、メッシュとマテリアルだけ差し替える構造にする。
そうすると「コピー」は `SkeletalMesh` と `Material` の参照を差し替えるだけになる。

### 4-2. 顔の醜悪化

- ブレンドシェイプ（モーフターゲット）を 3 段階分作る：`Distort_01 / 02 / 03`
- 掴まれた回数に応じてウェイトを 0 → 1 で補間
- 併せてマテリアルを差し替える（血色、目の発光、テクスチャのブレンド）
- 振り向き演出中は専用のライティング／ポストプロセスをかける（コントラストを上げ、
  被写界深度で顔だけに寄る）

3 段階分のモーフを作るのは彫刻作業だが、**アバターが 1 体でも作れば残りは同じ変形量を
転写できる**（同一トポロジのため）。ここでもアバター統一が効いてくる。

### 4-3. アニメーション

必要な最小セット：

- 歩く / 走る / しゃがむ（既製アセットで可）
- **掴みに手を伸ばす**（自作またはモーションキャプチャ）
- **掴まれて振り返る**（自作。ゲームの顔になるので手を抜かない）
- **ドッペルの追跡走り**（笑いながら＝上半身に別レイヤーを重ねる）
- 死亡 / 連れ去り

Mixamo で土台を取り、掴み・振り返りだけ自作するのが現実的。

### 4-4. マップ

- モジュラーアセット（壁・床・柱のパーツを組み合わせる）で作る
- **設計上の要件が明確にある**：見通しが効かないこと、ループ動線があること、
  行き止まりが少なすぎず多すぎないこと、隠れる場所があること
- 広間を作りたくなるが、広間は「同じ姿が 2 人いる」瞬間を安く見せてしまうので最小限に
- MVP は 1 マップで十分。むしろ 1 マップを詰めた方が良い
- ライティングはベイク中心（Lumen をフルで回すと 6 人分の描画が重い）

Synty / Quixel Megascans / Unreal Marketplace の廃墟アセットで初期は間に合う。

### 4-5. ボイスチャット

- Unreal：`VoiceChat` インターフェース + Vivox（Epic Online Services 経由で無料枠あり）
- Unity：Vivox、Photon Voice、または Odin
- Steam 前提なら Steam Voice API が最も安く単純

**距離減衰と遮蔽（壁越しでこもる）は必ず実装する。**これがないと
「ドッペルが遠くで探索の素振りをする」という立ち回りが成立しない。

## 5. MVP ロードマップ

各フェーズの終わりに「面白いか」を判定し、面白くなければ**次に進まず前に戻る**。

### Phase 0：紙・卓上プロトタイプ（3〜7 日）

3D を作る前に、ルールが成立するか机上で確かめる。

- マス目を描いた紙、コマ、各自が見える情報を制限した状態で回す
- 検証したいこと：背後の取り合いは駆け引きになるか、救助は間に合うか、
  「同じ姿が 2 人」は推理として機能するか
- ここで壊れているルールは 3D にしても壊れている

### Phase 1：グレーボックス・ローカル（2〜4 週間）

**最重要フェーズ。ここで企画の生死が決まる。**

- 箱と円柱だけの 3D 空間。テクスチャなし
- 実装するもの：移動、TPS カメラ、掴む、掴まれて振り返る（カメラ演出だけ）、3 回で死亡、救助
- **実装しないもの：**アイテム、スキル、時間ゲージ、ネットワーク、音、UI の作り込み
- 動作確認は 1 台のマシンで複数ウィンドウ（スプリットスクリーンまたはローカルマルチ）
- 判定基準：**「背後を取り合う数秒間が緊張するか」**。ここが面白くないなら企画を作り直す

### Phase 2：ネットワーク化と近接 VC（3〜5 週間）

- Steam リッスンサーバ、ロビー、6 人接続
- 正体の秘匿を 3-3 節の方針で実装
- 近接ボイスチャット（距離減衰）
- **ここで初めて 4〜6 人の実プレイテストができる。**心理戦が起きるかを確認する
- 判定基準：**「誰がドッペルか分からない時間が楽しいか」**

### Phase 3：ゲームループの完成（3〜5 週間）

- 時間ゲージと 3 フェーズ（夕刻・宵・深夜）
- 検証アイテム（まず鏡と懐中電灯の 2 種だけ）
- 変身のクールタイムと予兆
- 勝敗処理、リザルト
- 誤爆ペナルティ
- 判定基準：**「1 試合を通して山谷があるか」**

### Phase 4：演出と手触り（4〜8 週間）

- 顔の 3 段階変形、振り向き演出の作り込み
- 音響（足音、呼吸、悲鳴、環境音）
- マップを本番アセットで作り直す
- ライティング

### Phase 5：メタ進行とコンテンツ（継続）

- スキル 3 スロット、アンロック
- マップ追加、アバター追加
- マッチメイキング、リプレイ、実績

**Phase 1 + 2 だけで「遊べる」状態になる。**逆に Phase 5 を早く始めると必ず破綻する。

## 6. 体制と期間の目安

| 体制 | Phase 1〜3 到達 | 製品版 |
| --- | --- | --- |
| 1 人（兼務） | 4〜7 か月 | 2 年以上 |
| 2〜3 人（プログラマ＋アーティスト） | 3〜4 か月 | 10〜18 か月 |
| 5 人以上 | 2〜3 か月 | 8〜12 か月 |

個人開発でも Phase 1 は 1 か月以内に到達できる。**まずそこまでやること。**

## 7. リスク一覧

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ホストのチートで正体が丸見え | ゲームが根本から成立しない | 3-3 節。MVP は割り切り、公開時は専用サーバ検討 |
| 背後判定がラグで不公平 | 理不尽・炎上 | 3-2 節の予備動作方式で吸収 |
| 追跡が終わらない／逆に一瞬で終わる | テンポ崩壊 | 速度表（DESIGN.md 2-4）を実測で調整。最優先で詰める |
| ドッペル役が 1 人だけで待ち時間 | 離脱 | 連戦セット制、死亡者のドッペル化 |
| 同期人数が集まらない（6 人必須） | そもそも遊べない | 3 人（生存 2 ＋ドッペル 1）でも成立する調整を用意 |
| ボイスチャットなしだと成立しない | プレイヤー層が限定される | 定型コミュニケーション（ピン、簡易コマンド）を用意 |
| 顔の変形演出が予算を食う | 開発遅延 | アバター統一で 1 体分の作業を全体に転写 |

---

## 8. 最初の 2 週間でやること（具体的な着手手順）

1. **Phase 0 を回す。**紙とコマ、あるいは既存ゲーム（Among Us、Gorilla Tag など）で
   代替体験をして、背後の取り合いが成立するか確かめる
2. **エンジンを決めて、キャラを箱で動かす。**TPS カメラ、振り向き速度に上限をかける
3. **掴み判定だけ書く。**3-2 節の予備動作方式、ローカルで 2 体だけ
4. **3 回掴まれたら負け、を実装。**カメラを奪う 1 秒の振り向き演出を入れる
5. **知人 2〜3 人に触らせる。**背後を取り合う数秒が緊張するか、その一点だけ聞く

この 5 ステップの結果が良ければ、この企画は作る価値がある。
悪ければ、カメラ・速度・掴みの予備動作時間を変えて何度も試す。
アイテムもスキルもマップも、その後で構わない。
