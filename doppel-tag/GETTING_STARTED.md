## 5. 実装の方針で、先に決めておくべきこと

### 5-1. ダンジョンをグリッドで作る ── これが最重要

マップをテキストの升目として定義し、そこから箱を並べて 3D を生成する。

```
const MAP = [
  "###########",
  "#....#....#",
  "#.##.#.##.#",
  "#.#......A#",
  "#...####..#",
  "###########",
];
```

**これで 3 つの難所が同時に消える。**

1. **レベル制作にモデリングが要らない。**文字を書き換えれば地形が変わる。
   段階 1 で最も重要な「マップを何度も作り直して試す」ができる
2. **AI のパスファインディングが単純になる。**グリッド上の A\* で済む。ナビメッシュ不要
3. **AI 設計の中核である「視界コスト付きナビゲーション」（AI_DESIGN.md 4-2）が、
   グリッドなら各マスにコストを足すだけで実装できる。**
   本作の AI で最も効く技術が、最も簡単に書ける形になる

**本番でも、この方式のまま作り込む価値がある。**

### 5-2. 物理エンジンを入れない

必要なのは「壁にめり込まない」だけ。グリッドなので、
**円と升目の当たり判定を手で書けば 50 行程度**で済む。
物理ライブラリを入れると、設定と格闘する時間の方が長くなる。

### 5-3. 数値を全部 1 箇所にまとめる

**段階 1 の作業の本体は、コードを書くことではなく数値を調整することである。**

```ts
export const CONFIG = {
  moveSpeed: 3.0,          // m/s
  turnSpeed: 120,          // 度/秒（上限）
  lookBackSpeedMul: 0.6,   // 後ろを見ている間の減速
  grabWindup: 0.35,        // 掴みの予備動作（秒）
  grabRange: 1.5,          // m
  turnAroundLock: 1.0,     // 掴まれた時にカメラを奪う秒数
  aiChaseSpeedMul: 1.08,
  bandBack: 135,           // スプライト帯の幅（度）
  bandFront: 90,
  // ...
};
```

**ここを触りながら遊ぶのが段階 1 の本番。**
最初から調整しやすい形にしておかないと、検証そのものができない。

### 5-4. `THREE.Sprite` は使わない

**常にカメラを向いてしまう**ので、向きが画面に出ず企画が死ぬ
（SPRITE_PIPELINE.md 1 章）。`PlaneGeometry` を **Y 軸だけ**回して使う。

## 6. 段階 1 で実装するもの（この順で）

| # | 内容 | 完了の目安 |
| --- | --- | --- |
| 1 | Vite + three.js で箱が 1 つ表示される | 画面が出る |
| 2 | テキストマップから 3D の壁を生成 | 迷路の形が見える |
| 3 | プレイヤー移動＋壁の衝突 | ぶつかって止まる |
| 4 | 背後固定カメラ、回転速度に上限、Pointer Lock | 首だけ回せないことを確認 |
| 5 | **「後ろを見る」長押し**（減速する） | 前が見えなくなる |
| 6 | 4 方向スプライトの板ポリを 1 体置く | 回り込むと絵が切り替わる |
| 7 | 帯の判定（相手が自分に見せている帯の算出） | 画面に帯名をデバッグ表示 |
| 8 | 掴み：予備動作 0.35 秒 → 帯が「背面」なら成立 | 背後からだけ掴める |
| 9 | 掴まれ演出（1 秒カメラを奪う）＋ 3 回で敗北 | 負けられる |
| 10 | AI：グリッド A\* で追ってくるだけ | 逃げられる |
| 11 | 懐中電灯（`SpotLight`）と暗闇 | 見えづらくなる |
| 12 | 全部の数値を CONFIG に出して調整 | **ここからが本番** |

**7 と 8 が本作の心臓部。**ここだけは丁寧に作ること。

### 段階 1 限定のルール変更

本来「呪い状態のプレイヤーは掴み返せない」（救助が必要だから）が、
**1 人で検証する段階では、掴まれた後も掴み返せるようにしておく。**
そうしないと背後の取り合いという核が、1 人では試せない。

## 7. この段階で判定すること

**「後ろを取り合う数秒が緊張するか。」**これだけ。

自分で 30 分遊び、友人 2〜3 人に触らせて、同じ一点を聞く。

面白ければ → 段階 2（サーバとネットワーク）へ。
面白くなければ → **CONFIG の数値（特に移動速度、回転速度、予備動作時間、帯の幅）を
変えて何度も試す。**企画を捨てるのはその後でいい。

## 9. Unity（道 B）で行く場合の差分

| 項目 | 変わるところ |
| --- | --- |
| インストール | Unity Hub ＋ Unity エディタ（LTS 版）。Node.js は不要 |
| 言語 | C# |
| 助かること | エディタ、物理、キャラクターコントローラ、ナビメッシュが最初からある |
| 変わらないこと | **グリッド設計、CONFIG に数値を集める、実装順、判定基準は全部同じ** |
| 注意 | Unity の Sprite も既定でカメラを向く。Y 軸だけ回す形に自分で直すこと |

判断基準は BROWSER_TARGET.md 2 章。
**プログラミング経験が浅いなら Unity、全部自分で書きたいなら three.js。**
