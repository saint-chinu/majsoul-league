# P0：進行不能・データ損失・公開の前提条件

## P0-1　同 tick の順序が、2 箇所ともプレイヤー不利に倒れている

**問題**　仕様書自身が 2 件挙げている。

- 10.2：「水切れ猶予満了と最初の回復が同じ tick なら、脱落判定が回復より先」
- 11：「tick 冒頭に時間切れを判定するため、期限ちょうどの最後の保管は敗北が先」

**再現条件**　水切れ猶予の満了 tick で水に到達した場合。／残り時間ちょうどで最後の札を奉納した場合。

**影響**　どちらも**理不尽な敗北**として体験される。ぎりぎりの生還・ぎりぎりの勝利は
このジャンルで最も記憶に残る瞬間であり、それを 2 箇所とも取りこぼしている。
50ms の差は人間には知覚できないため、プレイヤーには「バグ」としか映らない。

**修正案**　tick 内の処理順を、**回復・達成を先に、消費・失敗を後に**へ入れ替える。

```
現行の想定：  時間切れ判定 → 入力処理 → 奉納 → 勝利判定
              水分消費 → 猶予満了判定 → 飲水回復

推奨：        入力処理 → 奉納 → 勝利判定 → 時間切れ判定
              飲水回復 → 水分消費 → 猶予満了判定
```

**同時成立は常にプレイヤー有利に倒す**を原則として明文化する。

**確認テスト**　猶予満了と同 tick の飲水で生存すること。試合期限と同 tick の奉納で勝利すること。
境界の前後 1 tick も併せて確認する。

**仕様変更**　必要（明文化されていないため、順序を仕様として定める）。

## P0-2　全状態配信により、開発者ツールだけでドッペルが判別できる

**問題**　16 節・20.5 節が記述するとおり、`kind`・`copyId`・全アイテム座標が配信されている。

**再現条件**　ブラウザの開発者ツールで WebSocket フレームを見るだけ。改造クライアントすら不要。

**影響**　**この問題は対戦ゲームより協力ゲームの方が深刻である。**
対戦なら「チートした本人が有利になる」だけだが、本作では **1 人が見るだけで、
その人が『あいつがドッペルだ』と言えば部屋全体の緊張が消える。**
14.1〜14.4 節が丁寧に積み上げた匿名出現・秘匿変身・ワープの設計が、すべて無効になる。

身内試遊では許容できるが、**一般公開の前提条件として P0 とすべき。**

**修正案**　`CLOUDFLARE_SPEC.md` 4 節。最小の対策は
**`kind` と `copyId` を配信しないこと**で、これだけで被害の大半が消える。
見た目は外見フィールドだけで表現でき、AI の偽装動作も本物と同一のイベントとして送れば区別できない。

**確認テスト**　開発者ツールで全フレームを目視し、種別・コピー元が含まれないこと。
1 試合分のフレームを保存し、機械的に検索して敵を特定できないことを確認する。

**仕様変更**　必要（「画面上の匿名性」だけでなく「通信データの匿名性」を要件に加える）。

## P0-3　掴まれ演出中に水切れ脱落が起きたときの整合性

**問題**　10.1：「`stunUntil` 中は自然消費を止める」「水切れ猶予期限そのものは別管理で、
**停止中にも到達し得る**」。

つまり**掴まれ演出（7／8／9.8 秒）の最中に、水切れで脱落する**状態が存在する。

**再現条件**　水分 0% の猶予 60 秒が残りわずかな状態で掴まれ、演出中に猶予が満了する。

**影響**　以下がすべて未定義：

- 本人の画面は顔演出中。そこへ水切れの脱落が割り込む。**どちらの演出が出るか**
- 敗北表示は『○○はドッペルに成り代わられた…』か、水切れの表示か
- **攻撃者の停止は解除されるか。**解除されないと、敵が最大 9.8 秒その場に残る
- `hits` は増えるか（掴みは成立している）
- 14.3 節の「脱落から 30 秒後に追加ドッペル」のタイマー起点はどこか

**修正案**　脱落原因に優先順位を定め、**一方の演出を確実に打ち切る**。
推奨は「掴み演出中は水切れ猶予の満了を保留し、演出終了時に判定する」。
掴まれている間は動けないので、プレイヤーに回避の余地がなく、保留しても不公平にならない。

**確認テスト**　猶予残り 3 秒で掴まれ、演出中に満了する状況を作る。
1／2／3 回目それぞれで確認する。

**仕様変更**　必要。

## P0-4　致死掴みのサーバー脱落と演出 9.8 秒のずれに伴う副作用

**問題**　7 節：「3 回目の掴み成立時にサーバー上は即脱落処理を行い、本人の演出が後から終わる。」

仕様書は「第三者視点・観戦との整合をレビューする」としているが、
**具体的に何がずれるかが列挙されていない。**

**再現条件**　3 回目の掴みが成立した直後の 9.8 秒間。

**影響**　以下が演出開始時に起きるのか終了時に起きるのかで、体験も公平性も変わる：

| 事象 | 検討点 |
|---|---|
| 所持していた札・装備の床への落下 | 即座なら、本人の画面ではまだ生きているのに他人が拾える |
| 観戦への切替（20.2 の 2.4 秒） | 演出 9.8 秒との関係 |
| 14.3 の「脱落から 30 秒後の追加ドッペル」の起点 | 起点が早いと、本人が観戦に入る前に敵が増える |
| 匿名通知「誰かの気配が消えた...！！」の発火時刻 | 演出開始時に鳴ると、**本人の演出が終わる前に他人が脱落を知る** |
| 第三者の画面での被害者の見え方 | 掴まれたままか、倒れているか |
| **演出中に第三者が攻撃者を撃退した場合** | 被害者は既に脱落済み。撃退しても救済にならないが、演出中に敵が消える。本人の画面はどうなるか |

**修正案**　**札のドロップ・匿名通知・追加ドッペルのタイマー起点を、演出終了時刻に揃える。**
サーバー内部の脱落確定は早くてよいが、**外部から観測できる事象の時刻を揃える**。
9.8 秒の演出中は攻撃者も停止しているので、ゲーム進行上の不利益はない。

**確認テスト**　3 回目の掴みから 9.8 秒間、第三者の画面・観戦画面・通知・床のアイテムを
毎秒記録し、演出終了前に脱落が漏れないことを確認する。

**仕様変更**　必要（どの事象をいつ発火するかを表として定める）。

# P1：ルールの穴・難易度・同期の納得感

## P1-5　60 秒クールダウンによる救助手段の枯渇

**問題**　6.1・6.2：探索者の掴みは成立から 60 秒。**仲間確認（誤爆）も同じ 60 秒を消費する。**
呪われた本人は掴めない。

**再現条件**　複数人が疑心暗鬼から仲間を掴んで確認し、その直後に誰かが呪われる。

**影響**　「掴んで確認する」がこのゲームの唯一の確定判別手段であり、
**同時に唯一の救助手段でもある。**両者が同じ 60 秒を共有しているため、

```
仲間を確認する → 60 秒間、仲間を救助できない
```

6 人全員がほぼ同時に確認を行うと、**最大 60 秒間チームに救助能力がゼロ**の窓ができる。
1 回目の演出 7 秒・2 回目 8 秒という短い救助機会に対して、60 秒は長い。
仕様書 P1-10 も同じ懸念を挙げているが、**設計上の相互作用としてより深刻**だと考える。

なお「確認にコストを払う」こと自体は良い設計である。問題は**コストの大きさと種類**。

**修正案**（いずれか、または組み合わせ）

| 案 | 内容 |
|---|---|
| A | **仲間確認（＝相手が探索者だった）だけ短縮**する（10〜15 秒）。ドッペル撃退の成功は 60 秒のまま |
| B | **撃退成功時はクールダウンを即リセット**する。うまく当てた人が動き続けられ、緊張が持続する |
| C | **呪われた仲間を救助する掴みだけ別枠**のクールダウンにする。確認と救助を分離する |
| D | 60 秒を 30〜40 秒へ短縮する |

**C が設計として最もきれい**（確認と救助という別の行為に、別のコストを割り当てる）。
ただし「目の前の相手が呪われているか」は画面で分かる必要がある。

**確認テスト**　6 人が 10 秒以内に全員仲間確認を行い、直後に 1 人が呪われる状況を作る。
救助が成立するかを確認する。

**仕様変更**　必要（バランス調整ではなくルールの変更）。

## P1-6　コピー元が呪われていると、敵が実質的に無限リスポーンする

**問題**　6.3：コピー元本人が撃退すると 23 秒退場、それ以外が撃退すると**3 秒後に別の姿で復帰**。
一方で、呪われた本人は掴めない。

**再現条件**　ドッペルが A の姿で A を追っている場合。

**影響**　A は呪い状態なので掴めない。他の人が撃退しても**3 秒で別の姿になって戻ってくる。**
最も効果的な「コピー元による長期撃退」が、**最も必要な場面で構造的に使えない。**

仕様書も 6.3 末尾で「この制約とコピー元本人による長期撃退の両立は、
協力の難易度として要評価」と書いているが、**単なる難易度ではなく、
ドッペルが自分のコピー元を追うことで自動的に無敵に近くなる**という
戦術的な抜け道になっている可能性がある。AI がこの状況を優先的に選ぶなら、なおさら。

**修正案**

| 案 | 内容 |
|---|---|
| A | **被害者がコピー元なら、誰が撃退しても長期退場**にする。「コピー元が関わった撃退」で判定する |
| B | 3 秒復帰を、同一試合内で撃退されるほど段階的に延ばす（3 → 8 → 15 秒） |
| C | 短期復帰した敵は、一定時間**追跡を再開しない**（別の探索者を狙う） |

**A が最も直接的に穴を塞ぐ。** B は雪だるま式の敗北（P1-8）の緩和にもなる。

**確認テスト**　A の姿のドッペルが A を追う状況を作り、B が撃退した場合の退場時間と
復帰後の追跡対象を確認する。AI がこの状況を選好しないかも併せて確認する。

**仕様変更**　必要。

## P1-7　生存者が多いほど敵が強く、脱落者が多いほど敵が弱いという逆転

**問題**　6.3 の表：通常敵はコピー元以外が撃退すると 3 秒復帰。
**脱落者由来の AI は「誰が掴んでも 23 秒」。**

**再現条件**　常時。

**影響**　**脱落者が増えるほど、個々の敵は撃退しやすくなる。**
数は増えるが質は下がるという逆転が起きている。

これは救済としては機能するが、意図した設計かどうかが仕様書から読み取れない。
14.3 節は「敵の数が増えること、必要お札が減らないこと、後半に水が減ることが重なるため、
逆転可能性は実プレイで調整する」としており、**むしろ難易度上昇を懸念している。**
実際には撃退のしやすさで一部相殺されている可能性があり、
**調整の前提が実態とずれているおそれがある。**

**修正案**　意図的なら仕様書に「脱落者由来の敵は撃退しやすい（救済措置）」と明記する。
意図的でないなら、P1-6 の案 B（段階的な復帰時間延長）で通常敵と揃える。

**確認テスト**　3 人脱落時点の敵構成（通常 2 体＋脱落者由来 3 体）で、
残存者が撃退を重ねた場合の実効的な敵密度を計測する。

**仕様変更**　明文化が必要。

## P1-8　掴みボタンの表示と判定が別時点の状態を使う

**問題**　6.1 のレビュー重要点：「ボタン表示とサーバー処理は別時点の状態を使う。」
クライアントは 100ms 補間の他者表示で判定し、サーバーは最新状態で判定する。

**再現条件**　RTT 150〜300ms、相手が 4.4m/s で移動中。

**影響**　RTT 300ms なら、ボタンが光ってから押してサーバーに届くまで実質 400ms 以上。
その間に相手は約 1.8m 動く。開始射程 2.1m ＋ 完了時許容 0.3m に対して**ほぼ全部を食う。**

**60 秒クールダウンがあるため、1 回の失敗の重みが極めて大きい。**
仕様書は「押せないときの空振りで 60 秒を消費しない」としているが、
これは「対象がいない」場合の話であり、**押した瞬間には条件を満たしていたのに
サーバーで不成立になった場合**にクールダウンを消費するかは要コード確認。

**修正案**

1. **サーバーが `grabbableTargetId` を配信する。**表示と判定の根拠を一致させる。
   表示は 50〜150ms 遅れるが、**「光ったのに失敗する」が原理的に消える。**
   本作は照準を必要としないので、この遅れは体感に影響しない
2. 成立しなかった掴みでは**クールダウンを消費しない**（要コード確認。
   消費している場合は最優先で直す）
3. 距離許容を固定 0.3m ではなく、**相手の速度 × 推定 RTT** に応じて増やす

**1 と 2 の組み合わせを推奨。**

**確認テスト**　人工 RTT 300ms で、ボタン点灯中に押した場合の成立率を計測する。
不成立時にクールダウンが消費されないことを確認する。

**仕様変更**　必要（配信データに追加）。

## P1-9　被掴み演出中に水分消費が止まる ＝ 苦痛が資源的な利益になる

**問題**　10.1：「`stunUntil` 中は自然消費を止める。掴み演出だけでなく、
ほかの停止でも同じ条件が適用される。」

**再現条件**　掴まれる（1 回目 7 秒＋2 回目 8 秒＝ 15 秒）。仲間確認（3 秒）。殴られる（1 秒）。

**影響**　水分は 120 秒で 0 になる設計。掴まれ演出 15 秒は**全体の 12.5% に相当する。**
つまり**掴まれた方が水分的に有利**という逆インセンティブが発生している。

即座に悪用可能とは言えない（呪い・脱落のリスクの方が大きい）が、
**終盤に水が枯渇する設計（10.3）と組み合わさると、
「わざと掴まれて水分を温存する」が合理的な選択になりうる。**
とくに `hits` が 1 の段階では、2 回目までの余裕がある。

**修正案**　停止中も自然消費を続ける。
ただし**掴まれている間は飲水できない**ため、消費を続けると理不尽側にも振れる。
推奨は**消費を半減**（止めるでも通常でもなく中間）。
仲間確認の 3 秒停止だけは、能動的な行為なので通常消費を維持する。

**確認テスト**　1 回目・2 回目に掴まれ、演出前後の水分を記録する。
意図的に掴まれ続けた場合の生存時間を、掴まれない場合と比較する。

**仕様変更**　必要。

## P1-10　天井落下：「救助できる」が実質的に機能しない／本人が何もできない 3.3 秒

**問題 A**　14.5 の発生条件は「他の生存探索者が **12m 以内におらず**」。
一方で「着地した 0.55 秒以降は呪われていない仲間が通常の背後判定で救助できる」。

**再現条件**　天井落下の発生時。

**影響**　12m 以上離れた仲間が到達するには、4.4m/s で約 2.7 秒かかる。
敵が動き出す 3.3 秒までに到着しても、**背後 135 度を取る余裕はほぼない。**
「救助できる」は仕様上の整合性のための記述であって、実プレイではまず起きない。

自動テストで「救助できる」を検証しても、**実プレイの挙動を保証しない。**

**問題 B**　より重要なのは体験の方。呪われた本人は掴めない（6.1）。
したがって**目の前に 3.3 秒間無防備な敵がいるのに、本人は何もできない。**
これは恐怖ではなく**苛立ち**として受け取られるおそれがある。

**修正案**

- 問題 A：仕様書に「救助は名目上の整合であり、実際にはほぼ発生しない」と明記するか、
  発生条件の 12m を緩める
- 問題 B：**天井落下中だけは、呪われた本人も掴めるという例外を設ける。**
  演出が同時に**唯一の自力反撃の機会**になり、
  「怖いだけで何もできない 3.3 秒」が「怖いが勝機でもある 3.3 秒」に変わる。
  発生率 30%・呪い 1 回につき 1 回という制限があるので、撃退が容易になりすぎることはない

**問題 B の修正は、この演出の価値を大きく上げると考える。**

**確認テスト**　天井落下発生時に本人が掴みを試み、意図どおりに成立／不成立となること。
仲間が 12m から走って救助を試み、実際に間に合うかを計測する。

**仕様変更**　必要（6.1 の「呪い中は掴めない」への例外追加）。

# P2：仕上げ・運用・公開準備

## P2-11　効果音 8.0MB が非圧縮 WAV

**問題**　8.1：「48kHz・16bit PCM、実行時の音素材は計約 8.0MB。」

**影響**　携帯回線での初回読み込みが重い。20.2 は「Three.js 約 530kB のサイズ警告」に触れているが、
**音声 8MB の方が 15 倍大きい。**「スマホの初回読み込み評価は残る」という課題の主因は
おそらくこちら。

**修正案**　Opus（96〜128kbps）へ変換する。**おおむね 1/10** になる。
短い衝撃音は圧縮劣化がほぼ問題にならない。
どうしても非圧縮で残したい素材だけ WAV に留める。
ダッキングやピーク制限はデコード後の Web Audio 上で行うので影響を受けない。

BGM を追加すると総量がさらに増えるため、**BGM 導入と同時に行うのが合理的。**
詳細は `BGM_SPEC.md` 6-2。

**確認テスト**　変換前後の総バイト数と、8.1 のピーク測定（0.90922）の再測定。
モバイル回線相当（4G・低速）で初回読み込み時間を計測する。

**仕様変更**　不要（実装の改善）。

## P2-12　状態配信が JSON・全量・20Hz

**問題**　16 節：「状態は部屋ごとに一度 JSON 化し参加者へ配信」、20Hz。

**影響**　actor 11 体＋item 20 個で 1 フレーム 2〜4KB とすると、
**1 人あたり下り約 480 kbps。**電波の弱い場所では厳しい。
DO 側も毎 tick `JSON.stringify` を実行する。
16 節が挙げる「`bufferedAmount` が取れず送信詰まりを保護できない」問題も、
そもそも送信量が多いことが前提にある。

**修正案**　`CLOUDFLARE_SPEC.md` 3 節。効果が大きい順に
(a) 送らないものを決める（P0-2 の対策がそのまま帯域削減になる）、
(b) 差分配信＋定期フルスナップショット、(c) バイナリ化。
**(a) だけでも相当減る。**

**確認テスト**　6 人接続時の 1 人あたり下り帯域を実測する。人工的に帯域を絞った環境で通しプレイ。

**仕様変更**　不要（配信形式の実装変更。ただし P0-2 は仕様変更）。

## P2-13　明滅・光感受性への配慮が未実装のまま公開に進もうとしている

**問題**　20.5：「点滅軽減設定は未実装。」
8 節：呪いノイズ（0.19 秒 ×2.4 秒周期）、水切れの赤点滅（2.4 秒周期）、暗転、顔アップ。

**影響**　個々の周期は一般的な閃光基準に触れないと思われるが、
**重なったときの実測が行われていない。**8 節自身が
「ノイズ、暗転、水切れ赤点滅、顔アップが重なる場合の優先順位と視認性を確認する」と
課題にしている。

**一般公開する以上、これは「今後の検討対象」ではなく公開要件。**

**修正案**　「明滅を弱める」設定を実装する（各演出の強度に係数を掛けるだけで済む）。
起動時にコンテンツ警告を表示する。重畳時の実測を行う。

**確認テスト**　全演出を同時に発生させ、画面の輝度変化を記録して周期と振幅を測定する。

**仕様変更**　必要（20.4 の公開前残作業に追加）。

## P2-14　「試遊で調整する」の根拠となるデータを取る仕組みがない

**問題**　仕様書には「仮値」「試遊で調整」が 14 箇所以上あるが、
**調整の判断材料を収集する仕組みが記述されていない。**

**影響**　水の再出現間隔、60 秒クールダウン、30% 抽選、50% 変身、
65% の見逃し、18〜38 秒の偽装検討、6 分／12 分のクリア率——
これらを体感だけで調整するのは難しい。とくに確率が絡む項目は、
数試合の体感では判断できない。

**修正案**　試合終了時に匿名の集計レコードを 1 件送る。
項目は `CLOUDFLARE_SPEC.md` 8-2。実装は小さく、調整の質は大きく変わる。
個人を特定しない形にとどめ、プライバシーポリシーと整合させる。

**確認テスト**　1 試合完了後にレコードが 1 件だけ記録されること。
途中退出・切断・再挑戦で重複しないこと。

**仕様変更**　必要（新規機能）。

## P2-15　手鏡の顔判別距離 2.8m は実用に足りるか

**問題**　15.1：鏡で顔の変貌が見えるのは 2.8m 以内。
鏡使用中は移動・旋回・掴み・飲水・後方確認が停止し、無敵もない。

**影響**　プレイヤー速度 4.4m/s に対し、2.8m は**0.64 秒分の距離**。
角から差し出す運用でも、角の向こう 2.8m 以内に敵がいる状況は限られる。
一方でコストは高い（完全に無防備）。

**「掴んで確認」は 60 秒のコストだが確実。鏡は無防備だが不確実。**
この比較で鏡が選ばれないなら、実装量に対して使われない機能になる。

なお**「出現・変身の瞬間を鏡だけで見破れる」（距離制限なし）は明確に強い価値**があり、
ここは良い設計。問題は顔判別の方。

**修正案**　プレイテストで 2.8m を 4〜5m まで広げる余地を見る。
あるいは鏡使用中も**ゆっくり後退できる**ようにして、無防備さを緩和する。

**確認テスト**　試遊で鏡の使用回数・使用時間・鏡による判別成功回数を計測する（P2-14）。
使用回数がごく少なければ、調整が必要という判断材料になる。

**仕様変更**　不要（仮値の調整）。

## P2-16　Git 未初期化のまま認証情報を扱っている

**問題**　20.4：「現ワークスペースはまだ Git リポジトリ未初期化。」
一方でアカウント・セッション・復旧コード・Cloudflare 連携を扱っている。

**影響**　最初の `git add -A` で、ローカル検証用のアカウント保存ファイル、
`.dev.vars`、`test-results/`、`.wrangler/` を巻き込む可能性がある。
一度履歴に入ると除去が面倒になる。

**修正案**　**最初のコミットの前に `.gitignore` を用意する。**
内容は `CLOUDFLARE_SPEC.md` 7 節。
23 節が「認証トークン等を含めない」と正しく書いているので、それを機械的に担保する。

**確認テスト**　`git status` で該当ファイルが追跡対象に含まれないこと。
初回コミット後に `git log -p` を検索し、秘密情報が含まれないこと。

**仕様変更**　不要。

# 優先順位の提案

| 順 | 項目 | 理由 |
|---|---|---|
| 1 | **P0-1（tick 順序）** | 修正が最も小さく、体験への効果が最も大きい |
| 2 | **P0-2（kind/copyId を送らない）** | 一般公開の前提。帯域削減（P2-12）も同時に達成 |
| 3 | **P0-3・P0-4（脱落まわりの整合）** | 進行不能・表示破綻の温床 |
| 4 | **P1-5・P1-6（60 秒と 3 秒復帰）** | ルールの根幹。実回線試遊の前に決めておく |
| 5 | **P1-8（掴みの表示と判定の一致）** | 実回線試遊の納得感を左右する |
| 6 | P2-11（音声の Opus 化） | BGM 実装と同時に行う |
| 7 | P2-14（テレメトリ） | **試遊の前に入れる。**後からでは初期の試遊データが取れない |
| 8 | P2-13（明滅軽減） | 公開要件 |
| 9 | その他 | |

**P2-14（テレメトリ）を実回線試遊より前に入れることを特に勧める。**
最初の試遊は最も情報量の多い機会であり、そこで測れなかったものは二度と同じ条件では測れない。
