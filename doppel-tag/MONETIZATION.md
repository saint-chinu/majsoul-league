# 収益化 — note でのアクセスパス販売案の検討

## 0. 結論

**仕組みとしては成立する。**決済・カード処理・税処理を note に丸投げできるのは実際に大きい。
Stripe を組んで特商法表記を整えて……という工程が丸ごと消える。

ただし**本作固有の問題が 2 つ**ある。

1. note では**「1 人 1 コード」が作れない**（コードが共有され放題になる）── 3 章
2. **協力ゲームは、入口に課金を置くと最も機能しなくなる** ── 4 章（こちらの方が深刻）

2 の方が重要なので、先に読んでほしい。

---

## 1. この案の良いところ

- **決済インフラを一切作らなくていい。**Stripe 統合、カード情報、返金処理、消費税——全部 note 側
- **今日から始められる。**サイトも法人も要らない
- **開発日誌と抱き合わせられる。**note は文章の場なので、
  制作過程を書きながら読者を育て、その延長で販売できる。ゲームの宣伝と収益化が同じ場所で回る
- 日本語圏の決済手段（カード、キャリア決済など）に対応している

手数料は決済手数料＋note の利用料で、カード決済ならおおむね **15〜20% 程度**。
Steam の 30% より安い。**（料率は変わるので、必ず最新の規約を確認すること。）**

---

## 2. 前提：パスの検証は必ずサーバ側で行う

ブラウザゲームはコードもメモリも完全に見える。
**パスワードの照合をクライアントでやると 5 分で破られる。**

幸い、本作は既に **Node の権威サーバを立てる前提**（BROWSER_TARGET.md 4 章、
ブラウザのタブが裏に回るとホストが止まる問題への対策）なので、置き場所は既にある。

```
1. ブラウザがコードをサーバへ送る
2. サーバが DB（SQLite で十分）のハッシュと照合
3. 通れば、そのコードをアカウントに束縛する（初回のみ）
4. 以後はアカウントでログイン。コードは再利用不可
5. 照合の試行回数を IP 単位で制限（総当たり対策）
```

コードは「ランダム文字列を生成して DB に入れるスクリプト」で作れる。実装は難しくない。

---

## 3. 問題 1：note では「1 人 1 コード」にできない

上の「初回にアカウントへ束縛する一回限りのコード」が理想だが、**note では実現できない。**

note の有料記事は、**購入者全員に同じ本文を見せる**仕組みだから。
購入者ごとに違うコードを出す機能も、購入を通知してくれる仕組み（Webhook や API）もない。
（この点は仕様変更の可能性があるので、実際に始める前に最新の仕様を確認すること。）

結果として：

- 記事の中に書いた**共通パスワードは、スクリーンショット 1 枚で無限に広がる**
- SNS に貼られたら終わり。1 人の購入で 1,000 人が遊べてしまう

### 回避策と、その限界

| 手 | 評価 |
| --- | --- |
| 有料部分に「コード配布ページ」への URL を置き、そのページが未使用コードを 1 つ渡す | **URL さえ漏れれば同じこと。**レート制限と定期的な URL 変更で延命はできる |
| 購入者に手動でコードを発行する | 確実だが、売れるほど自分の作業が増える |
| コードを定期的に失効させ、記事を更新する | 漏洩の被害を期間で区切れる。ただし正規購入者にも手間がかかる |

**どれも決定打にならない。**「1 人 1 コード」が要件なら、note 単体では足りない（7 章に代替案）。

---

## 4. 問題 2：協力ゲームは、入口の課金と最も相性が悪い

**こちらの方が重大。**

本作は 3〜6 人集まらないと成立しない。
アクセスに課金を置くと、**遊ぶために友人全員が買う必要がある。**

- 1 人 500 円でも、6 人集めるには「6 人全員に 500 円払わせる」という交渉が要る
- 誘われた側は、面白いか分からないものに先に金を払うことになる
- **本作最大の武器である「このリンク踏んで」が、そのまま使えなくなる**

BROWSER_TARGET.md で「配布が URL であることは協力ゲームにとって決定的に強い」と書いたが、
**入口の課金は、その強みを自分から捨てる行為**になる。

この理由から、協力ゲームは安く売る（Lethal Company は約 10 ドル）か、
基本無料にするか、**買った 1 人が友人を無料で招待できる**形を取ることが多い。

---

## 5. 本作に合う収益化の形（推奨順）

### 案 A：ホスト（部屋を立てる人）だけ有料 ── 最も相性が良い

- **遊ぶのは誰でも無料。参加にコードは要らない**
- **部屋を立てるにはパスが必要**

つまり **6 人につき 1 人が払えばいい。**
「このリンク踏んで」はそのまま生き、誘われた側の障壁がゼロのまま、収益が立つ。
払った人は「部屋主」という立場と機能を得るので、対価としても納得しやすい。

コードが漏れても被害は限定的（漏れた人が部屋を立てられるだけ）なので、
**問題 1 の深刻さも同時に下がる。**note で売るのに最も向いた形。

### 案 B：完全無料 ＋ コスメ課金

**本作はコスメ課金の器を既に持っている。**

ART_DIRECTION.md で「**魚＝試合内で一意、識別用／肉体＝重複可、自己表現のみ**」と
役割を分けたが、これは**識別に影響しない見た目だけを売れる**という意味でもある。

- 肉体（体格、肌の色）、ズボンの形・色・柄
- **ゲームバランスにも識別にも一切影響しない**ので、Pay-to-Win にならない
- 魚頭はランダム割り当てなので、絶対に売ってはいけない（識別が壊れる）

集客が回ってからでないと成立しないが、**協力ゲームの拡散力を一切損なわない。**

### 案 C：note のメンバーシップで「支援型」

月額の支援者向けに、開発日誌、先行アクセス、限定コスメ、要望の反映。
ゲーム本体は無料のまま。**個人開発と最も相性が良く、開発中から収入が立つ。**

### 案 D：ブラウザ版は無料、Steam 版を有料で売る

BROWSER_TARGET.md 3 章の推奨。ブラウザ版が体験版と宣伝を兼ねる。
本気で売る段階になったらこれを目指す。

### 組み合わせるなら

**「ブラウザ版は無料開放（案 B のコスメ ＋ 案 C の支援）→ 人が集まったら Steam 版（案 D）」**
が本命。note で売るなら**案 A（ホスト課金）**が最も無理がない。

---

## 6. どうしてもコードを売るなら：note 以外の選択肢

「1 人 1 コード」が要件なら、以下は note より仕組みが揃っている。

| サービス | 特徴 |
| --- | --- |
| **itch.io** | **ブラウザゲームをそのままホストし、購入者だけ遊べる形にできる。**ホスティング・決済・アクセス制御が全部込みで、本件に最も直接的に合う |
| **Gumroad** | **購入ごとに固有のライセンスキーを自動発行し、検証 API まで用意されている。**3 章の問題がそのまま解決する |
| **BOOTH（pixiv）** | 日本語圏の同人販売の定番。読者層と決済手段が国内向け |
| **pixivFANBOX** | note メンバーシップと同種の支援型。イラスト・ゲーム系の読者が多い |

**note の強みは「文章で読者を育てられること」**であって、アクセス制御ではない。
役割を分けるのが良い：

- **note**：開発日誌を書いて人を集める（宣伝と支援）
- **itch.io / Gumroad**：ゲーム本体の配信とアクセス制御

---

## 7. 先に決めておくこと

1. **入口を有料にするか、無料にするか。**ここが全ての分岐点。
   協力ゲームである以上、**無料開放を強く推す**
2. 有料にするなら、**案 A（ホストだけ有料）**にできないか検討する
3. コード方式を採るなら、**検証は必ずサーバ側**（2 章）。ブラウザで照合しない
4. 将来 Steam 版を出す場合、**note や itch.io で買った人をどう扱うか**を先に決めておく。
   後から「無料で引き換え」を用意しようとすると、購入記録の照合で苦労する
5. 料率・仕様は変わる。**始める前に各サービスの最新の規約を確認すること**
