# プラットフォームと技術スタック — モバイル目標を踏まえた選定

## 0. 決定事項

- 形式は**協力型マルチプレイ**（人間は全員味方、敵は AI のみ）。「対人戦」ではない
- 最終目標は**スマホアプリとしての販売**
- 直近の目標は**テストプレイできる状態**

---

## 1. まず、技術の前提について

> 「リアルタイムだから JS ではないものが必要だよね。一昔前なら Java と Flash アニメーション？」

3 点、現状を整理する。

### 1-1. JavaScript は今や十分に速い（が、本作では選ばない）

「JS はリアルタイム 3D に耐えない」という前提は、現在では正しくない。
WebGL / WebGPU 上で three.js、Babylon.js、PlayCanvas などが 60fps の 3D を普通に動かしている。
**性能上の理由で JS を外す必要はない。**

外す理由は別にある：**最終目標がネイティブのスマホアプリだから。**
ストア配信、課金、権限管理、ボイスチャット、省電力、低スペック Android への対応——
これら全てで、ブラウザ上の JS はプラットフォームと戦い続けることになる。
性能ではなく**出口**の問題として選ばない。

（ただし後述の通り、**テスト配布の手段としてのブラウザビルドは非常に有効**。）

### 1-2. Flash と Java アプレットはどちらも消滅している

- **Flash**：2020 年 12 月末でサポート終了。全ブラウザからプラグイン機構ごと削除済み
- **Java アプレット**：JDK 11 で削除済み。ブラウザ側の対応も終了

どちらも選択肢として存在しない。

### 1-3. 当時の「Flash アニメーション」に相当する現代の道具

やりたかったことは「2D アニメーションを効率よく作って動かす」ことのはず。現代の対応物は：

- **スプライトシート**（本作の SPRITE_PIPELINE.md で採る方式。3D からレンダリングして生成）
- **Spine / DragonBones**（ボーン付き 2D アニメーション。Flash の思想に最も近い）
- **Live2D**（立ち絵の変形に特化）

本作は 4 方向 × 少数のモーションなので、**スプライトシートで十分**。Spine は不要。

## 2. エンジン：Unity を推奨（前回の判断を変更）

TECH_PLAN.md 第 2 章では Unreal Engine 5 を推奨した。
**モバイルが最終目標になったことで、この判断は変わる。**

前回 UE5 を推した最大の理由は「キャラクター移動のネットワーク同期が標準で完成している」ことだったが、

- キャラクターは 2D スプライトになり、複雑なアニメーション同期が不要になった
- 移動も「常時走り・向き 4 方向・低速回転」と単純
- つまり **UE5 を選ぶ最大の理由が、設計変更によって消えた**

一方で **Unity を選ぶ理由が、モバイル目標によって決定的になった**。

| 観点 | Unity | Unreal 5 |
| --- | --- | --- |
| モバイル対応 | **本領。低スペック Android まで実績が厚い** | 重く、ビルドサイズが大きい |
| ビルドサイズ・起動時間 | 小さくできる | 苦戦する |
| 2D スプライトを 3D 空間に置く | 標準機能（Sprite Renderer、スプライトライティング） | できるが定石が薄い |
| PC でプロトタイプ → そのままモバイルへ | **同一プロジェクトで切り替え可能** | 可能だが調整が重い |
| ブラウザ配布（テスト用） | WebGL 書き出しあり | 実質不可 |

**結論：Unity。**
PC でテストプレイし、同じプロジェクトのままモバイルへ持っていける点が、本件では決定的。

### 対抗：Godot 4

無料で軽量、モバイル書き出しもあり、2D と 3D の混在も得意。
TECH_PLAN.md では非推奨としたが、2D キャラ化によって当時の懸念
（キャラクター移動の予測・補正の自作）は大幅に軽くなっている。

ただし、**リアルタイムのマルチプレイとストア運用の実績は Unity に劣る。**
商用のモバイル協力ゲームとしては Unity の方が安全。
「完全無償で、後々の実績よりも身軽さを取る」なら Godot も現実的な選択肢。

### 補足：Unity のライセンス

2023 年に問題になった実行時課金（Runtime Fee）は 2024 年に撤回され、
従来の座席課金に戻っている。無料の Personal 枠には収益のしきい値がある。
**条件は変わりうるので、着手前に必ず最新の規約を確認すること。**

## 3. ネットワーク：Steam 前提が使えなくなった

TECH_PLAN.md 3-1 では「Steam のリレー（SDR）でリッスンサーバ」を推奨したが、
**モバイルには Steam が存在しない。**ここは全面的に置き換わる。

### 3-1. 選択肢

| 方式 | 評価 |
| --- | --- |
| **Unity Netcode for GameObjects + Relay + Lobby** | Unity 純正。統合が楽で安価。**プロトタイプはこれで十分** |
| **Photon Fusion** | ネットコードの完成度が最も高く、モバイル実績も厚い。学習コストと同時接続数課金あり |
| Mirror ＋ 自前リレー | 無料だが運用を自分で持つことになる |
| Nakama | サーバ機能が豊富。オーバースペック気味 |

**推奨：まず Unity NGO + Relay + Lobby で作る。**
規模が見えてきた段階で、必要なら Photon Fusion へ移行を検討する。

### 3-2. モバイル固有の問題（設計に効く）

**遅延**：携帯回線では 100〜300ms が普通。だが本作は既に対策済みで、

- 掴みの 0.3〜0.4 秒の予備動作（TECH_PLAN.md 3-2）
- 判定を「表示中のスプライト帯」という整数で行う（SPRITE_PIPELINE.md 3 章）
- 掴まれた瞬間の 1 秒の振り返り演出

この 3 つが遅延を吸収する。**モバイルでも成立する設計に、偶然なっている。**

**バックグラウンド化**：スマホは着信・通知・ホームボタンでアプリが停止する。
ホストが停止するとセッションが死ぬ。対策：

- **1 試合 10〜14 分**という短さが効いている（既に決定済み）
- 復帰猶予を設ける（30 秒以内の再接続は同じ役で戻れる）
- ホスト離脱時は、ホスト移譲を諦めて「試合終了・結果は保存」と割り切るのが現実的
- 端末をホストにせず、Photon のようなクラウド権威型に寄せる手もある（費用と引き換え）

**通信量と電池**：近接ボイスチャットは携帯回線と電池を食う。設定で切れるようにすること。

### 3-3. PvE になったことで消えた問題（再確認）

正体秘匿のネットコード（ホストが真の正体を覗ける問題）は、
敵が AI になったことで消滅している。モバイルの P2P でも問題にならない。

## 4. 操作系：実はモバイルに向いている

本作の操作は驚くほど少ない。

| 操作 | モバイルでの割り当て |
| --- | --- |
| 移動 | 左手のバーチャルスティック |
| 向きを変える | 画面右側のドラッグ（キャラごと回る。回転速度に上限） |
| **後ろを見る** | 右手の大きな専用ボタン（長押し） |
| 掴む | 右手のボタン |
| 調べる／ライト | 文脈ボタン |

- 精密な照準が要らない
- 常時走りなので歩き／走りの切り替えが要らない
- ジャンプもしゃがみも（今のところ）要らない

**このゲームは、設計上たまたまモバイルに非常に適している。**
ただし**「後ろを見る」ボタンは最重要操作**なので、押しやすさと誤爆のしにくさを
最優先で配置すること。ここの操作感がゲームの質を直接決める。

## 5. ボイスチャット

本作の設計はボイスチャットに依存している（位置の確認、AI の声の録音再生）。

- モバイル対応の選択肢：**Vivox**（Unity 統合）、**Agora**、**Photon Voice**
- マイク権限、電池、通信量という追加コストが発生する
- **プッシュトゥトーク**を既定にすると電池と通信量が大幅に減る

**代替手段も必ず用意すること。**ボイスなしでも遊べるように、
「ここにいる」「危ない」「助けて」「合流しよう」程度の定型ピンを実装する。
モバイルでは音声を使わない層が一定数いる。

## 6. テストプレイできる状態までの最短経路

**最も重要な助言：最初のテスト版は、ネットワークもモバイルも入れないこと。**
両方を同時に始めると、面白いかどうかを判定できないまま数か月が溶ける。

### 段階 1：PC・1 人・キーボード（約 2 週間）

- Unity、箱と円柱だけのダンジョン
- 4 方向スプライト（仮絵で可。棒人間で十分）
- 移動、向き変更、**後ろを見る**、掴む
- AI ドッペル 1 体（最短経路で追ってくるだけ。擬態なし）
- 3 回掴まれたら負け

**判定したいこと：後ろを取り合う数秒が緊張するか。**
ここが面白くなければ、ネットワークもモバイルも意味がない。

### 段階 2：PC・3〜4 人・ネットワーク（約 3 週間）

- Unity NGO + Relay + Lobby
- 近接ボイスチャット
- AI に視界コスト付きナビゲーションと襲撃中断を実装（AI_DESIGN.md 段階 2〜3）

**配布方法：Unity の WebGL 書き出し。**
URL を送るだけで友人が遊べる。インストールもストアも不要で、
**この段階の検証速度が段違いになる。**（WebGL でボイスチャットまで通すのは面倒なので、
音声は Discord などで代用して構わない。）

**判定したいこと：みんなで凌ぐのが楽しいか。**

### 段階 3：擬態とディレクター（約 4 週間）

- 魚頭のランダム割り当て、コピー、変身（AI_DESIGN.md 段階 4〜5）
- ここで初めて「ドッペル鬼ごっこ」になる

### 段階 4：モバイル移植（約 3〜4 週間）

- タッチ操作、UI の再設計、性能調整
- Android 実機を先に（配布が簡単）。iOS はその後
- **配布**：Android は APK の直接配布か Google Play の内部テスト、
  iOS は TestFlight

### 段階 5：製品化

- 本番アセット、マップ、演出、課金、ストア対応

**段階 1 と 2 で、この企画が成立するかの答えが出る。**
そこまでを最速で到達することだけ考えること。

## 7. 「協力ゲーム」であることの帰結

人間は全員味方で、敵は AI のみ——これはストアページと宣伝の書き方に直結する。

- **「対人戦」「PvP」と書かないこと。**期待を裏切ると評価が下がる
- 使うべき言葉は「協力」「Co-op」「みんなで生き延びる」
- 参照すべき棚は Lethal Company / Content Warning / Phasmophobia であり、
  Dead by Daylight ではない

モバイルでの協力ゲームは、**一緒に遊ぶ相手を集める手段**が生命線になる。

- 招待リンク／部屋番号でのシンプルな合流（アカウント連携を必須にしない）
- 3 人で成立する設計（AI_DESIGN.md 6-4 の通り、3〜4 人なら AI 1 体）
- 野良マッチも用意するが、**まずは友人同士で遊べることを優先**

## 8. まとめ

| 項目 | 選定 |
| --- | --- |
| エンジン | **Unity**（対抗：Godot 4） |
| ネットワーク | **Unity Netcode for GameObjects + Relay + Lobby**（将来 Photon Fusion） |
| ボイス | Vivox / Agora / Photon Voice ＋ 定型ピンの代替手段 |
| キャラ表現 | 4 方向スプライトシート（3D からレンダリング） |
| 初期のテスト配布 | **Unity WebGL 書き出し（URL を送るだけ）** |
| モバイルのテスト配布 | Android 内部テスト → iOS TestFlight |
| JS / Flash / Java アプレット | 採用しない（性能ではなく、Flash と Java は消滅済み、JS は出口の問題） |
