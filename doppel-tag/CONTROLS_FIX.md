# 操作系の修正仕様 — 「まっすぐ歩けない」の原因と対策

現行仕様書 4 節（操作）・5 節（移動）への修正提案。
症状：**スマホで斜めを向いた後に上を押すと斜めに走り、まっすぐ歩けない。**

---

## 1. 原因は 2 つ重なっている

### 原因 A：入力の基準が「体」で、画面の基準が「カメラ」

現行：スティックの上 ＝ **体の正面方向**へ前進（体基準）。
一方、カメラは俯瞰の三人称で、**体の向きと画面の上が一致していない**。

体が斜めを向いていれば、「上」を押すと画面上は斜めに走る。
これは実装の不具合ではなく、**入力の座標系とカメラの座標系が別物**という設計上の不一致。

3D ゲームの標準は「入力はカメラ基準で受け、ワールド座標に変換し、体をそちらへ回す」。
体基準の入力は、**カメラが体に完全に固定されているときだけ**成立する
（その場合は両者が一致するので区別がつかない）。俯瞰や追従遅れのあるカメラでは破綻する。

### 原因 B：タッチスティックの左右が「旋回」に割り当てられている

現行のスマホ：右スティック**上下＝前後移動、左右＝体の旋回**。いわゆる戦車操作（タンクコントロール）。

これは物理スティック以上にタッチで致命的になる。理由：

- 親指は「真上」を正確に維持できない。常に数度ずれる
- 左右が**旋回**だと、そのずれが**時間で積分される**。数度のずれが毎秒 2.8 rad の一部として
  回り続け、1 秒後には明確に曲がっている
- 左右が**移動方向**なら、ずれは**その瞬間の進行方向が数度ずれるだけ**で、積み重ならない

**「まっすぐ歩けない」の直接原因はこちら。**原因 A を直しても、
スティック左右が旋回のままなら、まっすぐ歩けない症状は残る。

なお PC 版は「A/D 左右移動（ストレイフ）」があり、スマホ版だけが純粋な戦車操作になっている。
**PC とスマホで操作モデルが違う**ことも、スマホの感触が悪い一因。

---

## 2. 修正方針

### 2-1. 入力はカメラ基準（画面基準）で受ける — 常に

スティック（または WASD の合成ベクトル）を**画面座標**として受け取り、
**カメラのヨー角**でワールド座標へ回す。体のヨー角は使わない。

これはカメラの種類に関係なく正しい。追従カメラでも俯瞰でも、
「上を押せば画面の上へ進む」が常に成立する。

### 2-2. 体の旋回速度の上限は維持する — ここが本作の核

画面基準にしても、**体が瞬時に向きを変えてはいけない**。
体は目標方向へ**最大 2.8 rad/s（現行値）**で回る。真後ろへ向くには約 1.1 秒かかる。

これにより：

- 「振り向くには時間がかかる」という背後取りの緊張が保たれる
- 8 方向スプライトと背後 135 度の判定は**体のヨー角**の関数のまま。変更不要
- 後方確認（Q / Space 長押し）の存在意義も保たれる

**瞬時に向きが変わるスナップ回転にすると、ドッペルは永久に背後を取れなくなる。**
ここは絶対に緩めないこと。

### 2-3. 体の向きと違う方向へも動ける（PC の S・A/D と同じ扱い）

体が目標方向へ回りきる前も、スティック方向へ移動を始める。
ただし**向きと進行方向のずれに応じて減速**する。

```
align       = cos(体のヨー − 目標方向のヨー)     // 1 = 正面, −1 = 真後ろ
speedFactor = lerp(reverseFactor, 1.0, (align + 1) / 2)
```

`reverseFactor` は CONFIG で調整（初期値 0.6。現行の「後方確認中 60%」と揃える）。
真後ろへ後ずさりは 60% 速度、旋回が終わると 100% に戻る。

PC の S キー（後退）と A/D（横移動）は既にこの挙動なので、スマホを PC に揃えることになる。

### 2-4. 方向のラッチ — 追従カメラで必須の処理

追従カメラ（体の向きにカメラが追いつく）と画面基準入力を素朴に組み合わせると、
**反転時にスパイラルする**。

```
下を押す → 体が回り始める → カメラも追従して回る
→ 「下」の意味するワールド方向も回る → 目標方向が逃げ続ける → 体が円を描く
```

対策：**スティックを押した瞬間のカメラ角で目標方向を確定し、押している間は
カメラが回っても目標方向をワールド座標で固定する。**
スティックの角度を動かしたら、その**差分だけ**目標方向を回す。

```
毎フレーム:
  if |stick| < deadzone:
      desiredYaw = null
      prevStickAngle = null
  else:
      stickAngle = atan2(stick.x, stick.y)          // 画面の上 = 0
      if desiredYaw == null:
          desiredYaw = inputRefYaw + stickAngle      // 押した瞬間のカメラ基準
      else:
          desiredYaw += wrap(stickAngle − prevStickAngle)   // 以後はスティックの差分だけ反映
      prevStickAngle = stickAngle

  if desiredYaw != null:
      bodyYaw = turnToward(bodyYaw, desiredYaw, maxTurnRate * dt)
      align = cos(bodyYaw − desiredYaw)
      speedFactor = lerp(reverseFactor, 1, (align + 1) / 2)
      velocity = unit(desiredYaw) * baseSpeed * |stick| * speedFactor
```

`inputRefYaw` は**カメラのヨー角**。ただし次項の例外がある。

### 2-5. 後方確認中の入力基準 — 実装したら即座に踏む落とし穴

後方確認中はカメラが後ろを向く。
このとき `inputRefYaw` にそのままカメラ角を使うと、**「上」を押し続けているのに
後方確認を始めた瞬間に進行方向が反転する。**走って逃げながら後ろを見る、という
最も重要な操作が壊れる。

対策：カメラの「表示ヨー角」と「前方ヨー角」を分けて持つ。

| 変数 | 内容 |
|---|---|
| `cameraForwardYaw` | 追従カメラが追っている前方の角度。後方確認では**変えない** |
| `cameraDisplayYaw` | 実際の描画角。後方確認中は `cameraForwardYaw + π` |

`inputRefYaw` には**常に `cameraForwardYaw`** を使う。
これで後方確認の開始・終了で進行方向が変わらない。

手鏡モードは移動を停止するので影響しない。
仲間確認・被掴みの停止中は入力を無視するので影響しない。

### 2-6. スマホのスティック割り当て

| 現行 | 修正後 |
|---|---|
| 上下＝前後、左右＝**旋回** | **全方向＝画面基準の進行方向。旋回は体が自動で追従** |
| 画面スワイプ＝旋回 | 画面スワイプ＝**カメラの旋回**（`cameraForwardYaw` を回す）。任意 |

旋回をスティックから外すことで原因 B が消える。
カメラを手動で回したい場合だけスワイプを使う。使わなくても遊べる状態にする。

**移動スティックが右側にある配置は非標準**（大半のゲームは左スティック移動・右側アクション）。
意図した配置なら維持してよいが、初見の違和感の一因になりうるので、
設定で左右入替を用意することを推奨する。

### 2-7. PC

- WASD は合成ベクトルを画面基準で扱う（2-4 と同じ処理）。追従カメラなら体感は変わらない
- マウス左右・左右矢印は**カメラの旋回**（`cameraForwardYaw`）。体はそれに追従して回る
- 結果として PC とスマホが同じ操作モデルになる

## 3. カメラについて — 俯瞰の程度が核心に触れる

現行仕様 1 節「俯瞰の三人称カメラ」。**この俯瞰がどの程度かで、ゲームの成立が変わる。**

| カメラ | 判定 |
|---|---|
| **後ろ上方からの追従カメラ**（体の向きに緩やかに追いつく。自分の真後ろは映らない） | **推奨。**元の設計。「自分の背中しか見えない」が保たれる |
| 固定北向きの真上見下ろし（体が回っても画面は回らない） | **不可。**自分の背後が常に見える。後方確認の意味がなくなり、背後から忍び寄る緊張が消える |

固定北向きの俯瞰は、原因 A の症状（斜めに走る）を最も強く出す構成でもある。
**もし現行がこれなら、入力を画面基準にしても「見え方」の問題は残る**ので、
カメラを追従型へ変えること。

追従カメラの推奨値（CONFIG で調整）：

| 項目 | 初期値 |
|---|---|
| 追従の時定数 | 0.35 秒（`cameraForwardYaw` が体のヨーへ指数的に近づく） |
| 俯角 | 25〜35 度（背後は映らず、足元と数 m 先は見える） |
| 体からの距離 | 3.5〜4.5 m |
| 手動旋回（スワイプ／マウス）後の自動追従再開 | 入力が止まって 1.0 秒後 |

## 4. 「前の方がまだよかったか」への答え

**元の設計（背後固定カメラ＋体基準の前進）は、構造的にこの症状が出ない。**
カメラが体に固定なら「前 ＝ 画面の上」が常に成立するため、体基準と画面基準の区別がない。

現行は「俯瞰カメラ」と「体基準の戦車操作」という、**互いに最も相性の悪い組み合わせ**になっている。
戦車操作はカメラ固定の旧作ホラーでは成立していたが、
それは固定カメラの画角が戦車操作を前提に設計されていたから。俯瞰の追従カメラでは成立しない。

ただし**戻すのではなく、2 節の修正を入れる**のが正しい。
画面基準入力＋旋回速度上限＋ラッチは、追従カメラでも俯瞰でも正しく動き、
元の設計の「背中しか見えない」「振り向くには時間がかかる」をそのまま保つ。

---

## 5. 変わらないもの（確認）

- 8 方向スプライトの選択（体のヨー角で決まる）
- 背後 135 度の掴み判定（体のヨー角で決まる）
- 旋回速度 2.8 rad/s
- 後方確認の速度 60%
- 手鏡モードの身体回転（A/D で ±135 度）— 別系統のまま
- 掴み・飲水・仲間確認の停止処理

**判定と表示は一切触らない。**入力の解釈と、カメラの追従だけを変える。

## 7. 受け入れ確認

| シナリオ | 期待する結果 |
|---|---|
| 斜めを向いた状態で上を押す | **画面の上へ進む。**体が回りながら加速し、約 1 秒で正面を向く |
| 上を 10 秒押し続ける（タッチ） | 進行方向が 5 度以上ずれない。**曲がり続けない** |
| 走行中に下へ倒す | 60% 速度で後ずさりしつつ体が回る。約 1.1 秒後に反転して 100% |
| 反転中に体が円を描く | **起きない**（ラッチの確認） |
| 上を押しながら後方確認を開始・終了 | **進行方向が変わらない。**カメラだけが後ろを向く |
| 後方確認中に左右へ倒す | 前方基準で左右へ動く（後方基準ではない） |
| スワイプでカメラだけ回し、その後放置 | 1 秒後に体の向きへ自動で戻る |
| PC で W を押しながらマウスで旋回 | カメラが回り、体が追従し、画面の上へ進み続ける |
| 8 方向スプライト・背後判定 | 従来のテストが全件そのまま通る |
| 人工 RTT 300ms | クライアント予測が同じ入力解釈を使い、補正で体が跳ねない |

## 8. サーバーとの整合

16 節：「自分の移動はクライアント予測し、サーバー応答で補正。」

**入力の解釈（2-4 の計算）はサーバーとクライアントで同一のコードを使うこと。**
現行の入力は「移動軸・旋回」を送っているが、画面基準にするなら
**「目標ワールド方向（`desiredYaw`）と入力の強さ」を送る**方が、
サーバー側でカメラ角を知る必要がなくなり単純になる。

サーバーは `desiredYaw` を検証（数値範囲のみ）し、旋回上限と速度計算を自分で行う。
クライアントが体のヨー角を直接送ることは引き続き禁止。
